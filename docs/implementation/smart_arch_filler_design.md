# AI驱动的智能架构补全系统 (SmartArchFiller)

## 一、背景与挑战

当前系统 (`clarifier_v2`) 只基于架构文件进行浅层分析，导致：
- 结构化摘要 (`full_summary.json`) 中大量字段为空
- 没有多轮深度推理完善架构细节
- 缺乏结构一致性验证与冲突检测
- 未保存推理过程用于上下文增强

需要一个能进行深度自我推理、保证结构一致性、避免重复的智能补全系统。

## 二、系统架构

### 核心组件：
1. **Smart-Loop Processor**: 多轮自我问答推理引擎
2. **Context Manager**: 上下文检索与注入
3. **Consistency Validator**: 结构一致性与冲突检测
4. **Reasoning Logger**: 推理过程记录
5. **Dependency Graph**: 模块依赖关系管理
6. **Conflict Resolver**: 自动依赖冲突解决器

### 向量存储集合：
- `doc-index`: 原始文档片段
- `entity-summaries`: 结构化模块摘要
- `reasoning-log`: 推理对话记录
- `resolution-patterns`: 冲突解决模式库

## 三、核心流程

### 1. 智能推理循环 (Smart-Loop)
```
初始摘要 → [结构检查 → 上下文检索 → 自问自答 → 更新摘要] × N → 最终摘要
```

**每轮推理的关键步骤**：
- **结构检查**：验证schema、必填字段、依赖一致性
- **上下文检索**：原始文档 + 相似模块 + 历史推理
- **自问自答**：针对缺失/冲突字段，考虑行业最佳实践深度推理
- **摘要更新**：增量合并新信息，保留已有内容

### 2. 自问自答示例
```
Q: 作为auth_login模块，我需要哪些后端控制器方法？
A: 至少需要handleLogin和validateCredentials方法。

Q: 这些控制器调用什么服务？
A: 它们依赖AuthService进行身份验证和JWTService生成令牌。

Q: 前端需要什么组件？
A: LoginForm和AuthRedirect组件，以及authHook API调用钩子。
```

### 3. 依赖与冲突处理
```
预防式检测 → 自动解决策略应用 → 接口适配生成 → 模式学习 → 依赖图更新
```

**全自动冲突解决机制**：
- **预防式依赖检测**：在实体创建阶段就应用命名约束和领域边界规则
- **基于优先级的自动解决**：使用模块重要性和引用计数计算解决优先级
- **智能接口适配**：自动生成适配层，维护API兼容性
- **冲突模式学习**：记录并重用成功的解决方案

## 四、关键技术细节

### 1. 智能上下文注入
每轮推理中自动注入三类上下文：
- **原始文档片段**：`embedding_retrieve(entity_name, all_docs)`
- **相似模块摘要**：`retrieve_entity_summaries(entity_name)`
- **历史推理日志**：`retrieve_logs(entity_name)`

### 2. 结构一致性三层验证
- **Schema验证**：确保格式正确、必填字段存在
- **业务规则验证**：基于`field_rules.yaml`检查领域特定规则
- **依赖图验证**：检测命名冲突、循环依赖、孤立引用

### 3. 新模块重复检测
- **向量相似度**：计算与现有模块的相似度
- **字段差异分析**：比较API路径、方法名等关键字段
- **LLM辅助判断**：在边界情况下由LLM决定是否合并

### 4. 影响传播机制
当一个模块更新后，自动识别并更新所有依赖它的模块，确保整体一致性。

### 5. 元数据与可解释性
为每个生成的摘要添加元数据：
- 生成日期、信心分数
- 推理参考链接
- 支持证据来源

### 6. 多模型共识机制
关键决策采用多模型共识：
- 不同提示/模型同时请求
- 结果汇总或投票
- 不确定性量化与处理

### 7. 预防式依赖管理
- **命名约束规则**：基于项目惯例强制执行一致的命名模式
- **领域边界定义**：为每个模块设置明确的职责范围
- **早期冲突检测**：在设计阶段就评估潜在冲突

### 8. 自动冲突解决策略
- **优先级计算**：模块重要性 × 引用频率 × 修改复杂度
- **最小修改原则**：自动选择影响范围最小的解决方案
- **解决方案评分**：预测每个可能解决方案的成功率

### 9. 智能自适应接口
- **接口不匹配分析**：检测参数类型、命名、顺序差异
- **适配函数生成**：自动创建转换逻辑
- **兼容性检查**：验证适配层正确性

### 10. 冲突模式库
- **解决方案记忆**：存储每次成功的冲突解决
- **相似冲突检索**：基于向量相似度匹配历史案例
- **持续优化**：随系统使用不断完善解决模式

## 七、端到端工作流程：从文档到代码

### 1. 完整处理流程

**第一阶段：文档处理与基础理解 (clarifier_v2)**
- **目的**：理解项目架构文档，提取核心实体和结构
- **过程**：文档加载 → 向量化索引 → 实体识别 → 初步摘要生成
- **关键组件**：Document Loader, Entity Discovery, Structured Summarizer
- **输出**：初步结构化摘要 (`entity_summaries` 集合)

**第二阶段：智能推理与架构补全 (SmartArchFiller)**
- **目的**：深度理解架构，自主补充缺失细节，确保结构完整性
- **过程**：Smart-Loop 多轮推理 → 结构验证 → 冲突解决 → 完整摘要生成
- **关键组件**：Smart-Loop Processor, Context Manager, Consistency Validator, Conflict Resolver
- **输出**：完整结构化摘要 (`smart_modules_final/*.json`)

**第三阶段：代码生成与落地 (Generator)**
- **目的**：将完整架构转化为可运行代码
- **过程**：代码模板选择 → 组件实现 → 接口对接 → 单元测试生成
- **关键组件**：Code Generator, Test Generator, Integration Validator
- **输出**：完整可运行代码库

### 2. 工作流程示例

以"用户登录功能"为例：

**基础理解阶段 (clarifier_v2)**
- Entity Discovery 从文档中识别出 "auth_login" 实体
- Structured Summarizer 初步提取出它需要一个API和前端页面
- RAG Retriever 收集相关上下文存入 `doc-index`

**深度推理阶段 (SmartArchFiller)**
1. Smart-Loop Processor 启动多轮推理：
   - "一个登录模块通常需要哪些控制器方法？"
   - "验证身份需要什么服务？"
   - "前端需要什么组件和hooks？"

2. Context Manager 在每轮注入相关上下文：
   - 原始文档片段
   - 相似模块摘要（如其他认证相关模块）
   - 历史推理记录

3. Dependency Graph 检测新增依赖是否合理：
   - 检查 "AuthService" 是否存在
   - 分析 "JWTService" 的接口兼容性

4. Conflict Resolver 自动解决潜在冲突：
   - 生成缺失服务的接口规范
   - 调整命名以符合项目惯例

**代码生成阶段**
- 生成后端：LoginController.ts, AuthService.ts
- 生成前端：LoginForm.vue, AuthHook.ts
- 生成测试：LoginController.test.ts

### 3. 关键技术优势

- **上下文感知**：系统理解整个项目，而非孤立处理单个模块
- **自推理能力**：像资深架构师一样思考"应该有什么"而非只执行"告诉它做什么"
- **结构一致性**：自动确保所有生成内容遵循同一架构原则
- **自动冲突处理**：无需人工干预即可检测并解决依赖冲突
- **持续学习**：从每个项目积累经验，不断完善架构模式库
